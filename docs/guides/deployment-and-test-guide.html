Deploying and testing the Microsoft 365 Copilot connectors

A complete guide for someone who has never done this before. It assumes no prior knowledge of Microsoft 365, Microsoft Graph, SQL Server, PowerShell or this repository, and explains every term the first time it is used.

Applies to release v1.8.0. Allow one full day for a first deployment, and a second day for the tests.

Part 0. What you are building, and why

0.1 The problem this solves

Microsoft 365 Copilot answers questions using the documents and data it can see. Out of the box it sees things stored inside Microsoft 365 — email, Teams messages, files in SharePoint and OneDrive. It does not see anything in your own systems: your ticketing database, your HR system, your data warehouse.

A connector is the bridge. It copies information out of one of your systems and puts it into the Microsoft 365 search index, so Copilot can find it and answer questions about it. The information stays in your system too — the connector copies, it does not move.

This repository builds connectors that read from SQL Server databases and, optionally, from a Cloudera big-data cluster.

0.2 The two ways to build a connector, and which one this is

Microsoft offers two approaches, and it matters that you know which you are working with.

ApproachHow it worksWho does the work
Agent-hostedYou install Microsoft's "Graph connector agent" on a server. It calls your code on a schedule and handles everything else.Microsoft's agent handles scheduling, retries, change detection and deletions. You supply the data.
Direct push
(this repository)		Your own program reads the source and sends the data straight to Microsoft over the internet. There is no agent.You handle scheduling, retries, change detection and deletions. That is what most of this repository is.

Direct push gives you control and immediacy; the price is that everything the agent would have done for you has to exist in your own code. This repository contains that code. The guide below is about deploying and proving it.

0.3 The vocabulary, up front

You will meet these constantly. Read them once now; they are repeated in context later.

TermWhat it means
TenantYour organisation's Microsoft 365 account. Everything below happens inside one tenant.

0.4 The moving parts

By the end of this guide you will have five things running. Here is what each is for.

PartWhat it is and why it exists
The source databaseYour data. A SQL Server database the connector reads from, using a read-only login. The connector never writes to it.
The crawl state databaseA second SQL database, created by this repository. It remembers what was sent, when, and with what content — so the next crawl can send only what changed, and can tell what has been deleted. It also holds a lock that stops two crawls running at once.
The push toolsSmall command-line programs. You run one per source. Each reads its source, works out what to send, and sends it.
The external connectionsCreated inside Microsoft 365 by the tools on their first run. This is where the data lands.
The dashboardA small internal website showing crawl history and health. Read-only. Optional, but it is how you find out a crawl failed without reading log files.

The flow, in one sentence: a push tool reads rows from the source database, asks the crawl state database which of them have changed since last time, sends the changed ones to Microsoft Graph in batches, records what it sent back into the crawl state database, and removes from the index anything the source stopped returning.

0.5 The exit codes, and what each one means for you

When a push tool finishes it returns a number. In PowerShell you read it with $LASTEXITCODE. Learn these — your monitoring will be built on them.

CodeMeaningWhat to do
0SuccessNothing.
2Configuration is invalidThe tool refused to start. It prints every problem it found, not just the first. Fix the settings file. Nothing was sent.
3Credentials rejectedThe identity is wrong, expired, or lacks permission. Check the app registration and the stored secret. This is a security-team question, not a data question.
4Ingestion failedSomething went wrong partway. Some data may be in the index and some not. Read the log, fix the cause, run again — re-running is always safe.
5Skipped — already runningNot a failure. Another crawl of the same connection is already in progress and this one stood down deliberately. If your monitoring pages someone for this, it will page them for correct behaviour. Treat 5 as success.

1.4 Storing the secret safely

The client secret is a password. It must never go into a configuration file, because configuration files end up in source control, in backups, and in support bundles.

Store it in Windows Credential Manager, which encrypts it per-user on that machine:

cmdkey /generic:SqlGraphPush/EntraClientSecret /user:app /pass

It will prompt for the password — paste the secret there. The configuration file then contains only the name SqlGraphPush/EntraClientSecret, never the value. The connector reads it at startup, holds it in memory, and never writes it anywhere.

Confirm it is stored:

cmdkey /list | findstr SqlGraphPush

If the connector runs as a service account rather than as you, the credential must be stored under that account, because Credential Manager is per-user. Storing it as yourself and running as a service gives exit code 3 with a message about the credential not being found.

Part 2. Understanding what you are about to install

You could follow Part 3 mechanically. Do not. Five minutes here saves an afternoon later, because the commands in Part 3 fail in ways that only make sense if you know what they are doing.

2.1 Why there are two databases

The source database is yours and already exists. The connector only reads it.

The crawl state database is created by this repository, and exists to answer three questions nothing else can:

  • "Have I sent this item before, and has it changed?" It stores a fingerprint (a hash) of every item sent. Next time, the connector computes the fingerprint again; if it matches, it skips the item entirely. On a large corpus this is the difference between a 75-minute crawl and a 12-second one.
  • "What has been deleted?" Direct push has no notion of "no longer returned" — the source simply stops mentioning a row. By keeping an inventory of what it sent, the connector can compare and remove what has gone.
  • "Is another crawl already running?" Two at once is genuinely dangerous: each compares the source against its own partial view and offers the other's unprocessed items for deletion. A lease in this database prevents it.

If you skip the crawl state database the connector still works: it writes every item on every run and never deletes anything. That is a reasonable configuration for a one-off load and a poor one for a standing sync.

2.3 What a crawl actually does, step by step

Knowing this makes the log readable.

  1. Read the settings file and check every value. If anything is wrong it stops with exit 2 and lists all the problems, not just the first.
  2. Fetch the secret from Credential Manager and get a token from Microsoft.
  3. Create the connection if absent, then register the schema. Registration runs on Microsoft's side and takes 5 to 15 minutes. The connection sits in state "Draft" until it becomes "Ready".
  4. Take the lease in the crawl state database. If another crawl holds it, stop with exit 5.
  5. Open a run record, the numbered entry you will see in the dashboard.
  6. Read rows from the source, one at a time.
  7. For each row, work out who may see it, cut the text if it is too long, and compute two fingerprints, one for content and one for the access list.
  8. Every 200 rows, ask the state database which have changed. Send only those, in batches of 20.
  9. Record what was sent back into the state database.
  10. After a full crawl, compare the inventory against what the source returned and delete what is missing, unless that would exceed the safety threshold, in which case refuse and fail.
  11. Close the run record and print a summary.

2.4 How to read the summary line

Every run ends with a line like this. It is the most useful output the tool produces.

Ingestion complete. 111800 row(s) processed (Customer=1200, Engagement=6200, TimeEntry=104400)
for connection consultingwork; 111800 distinct item(s). unchanged=0 deleted=0 failed=0
batches=6252 truncated=0 skipped=0 duplicates=0 throttleWaits=3050
FieldWhat it tells you
processedItems actually written to the index this run.
unchangedItems whose fingerprint matched, so they were skipped. On a healthy second run this should be nearly everything.
deletedItems removed because the source stopped returning them.
failedItems Microsoft refused, which are NOT in the index. Anything above zero means data is missing, and the run exits 4.
batchesNetwork requests that carried the writes. Roughly items divided by 20.
truncatedItems whose text was cut to fit the size limit.
skippedItems deliberately not sent, usually because nobody could be granted access to them.
duplicatesThe source returned the same ID twice. Above zero means a defect in the source query.
throttleWaitsHow many times Microsoft asked the tool to slow down. Large numbers are normal and fine, provided failed is zero.

3.6 Write the settings file

Open C:\Connectors\SqlGraphPush\appsettings.json, the published one, not the one in the repository. It is JSON: text in quotes, values after colons, items separated by commas. A missing comma is the most common mistake and produces exit 2 naming the line.

{
  "Environment": "Production",

  "Auth": {
    "Mode": "ClientSecret",
    "TenantId": "<your tenant id>",
    "ClientId": "<your client id>",
    "ClientSecretCredentialTarget": "SqlGraphPush/EntraClientSecret"
  },

  "DataSource": {
    "Server": "<your sql server>",
    "Database": "<your source database>",
    "SqlAuthMode": "WindowsIntegrated",
    "MaxContentBytes": 3670016,
    "ExtraConnectionOptions": ""
  },

  "Acl": {
    "GrantGroupObjectIds": [ "<your entra group object id>" ]
  },

  "Graph": {
    "ConnectionId": "<yourconnectionid>",
    "ConnectionName": "A name people will see",
    "Description": "What this contains",
    "SchemaReadyTimeoutMinutes": 30
  },

  "Source": { "ItemView": "dbo.Tickets", "MaxItems": 0 },

  "Settings": {
    "Writers": "16",
    "Batch": "true",
    "StateConnectionString": "Server=<server>;Database=ConnectorState;Integrated Security=true;Encrypt=true"
  }
}

A note on SQL connection encryption. Both connection settings above leave certificate validation switched on, which is what you want. If your SQL Server has a self-signed certificate — common on a developer machine, and normal for a fresh local install — the connection will fail with a message about the certificate chain not being trusted.

There is a setting that turns that check off. This repository deliberately refuses to carry it: a committed secret scanner rejects it on sight, because switching off transport validation means anything on the network path can read your data in transit and nobody will be told. Do not add it to a production configuration.

The three legitimate answers, in order of preference: install a certificate the machine trusts; use a certificate from your internal authority; or, on a developer machine only and knowingly, add the exemption locally and never commit it. For one-off sqlcmd work against a local instance the -C flag does the same thing for that single command, which is why the examples earlier in this guide use it — a flag on a throwaway command is a different risk from a setting living permanently in a deployed file.

Things that will catch you here:

  • MaxItems: 0 means no limit, not "read nothing".
  • The state connection string must contain no password. The tool rejects one that does, because crawl state is reached with an integrated identity.
  • ConnectionId cannot be changed after the first run without deleting the connection and everything in it.
  • Leave Writers at 16. It is the ceiling; anything higher is silently clamped and the tool tells you so.

4.2 The first real run

.\SqlGraphPush.exe

Expect this to be slow the first time, and to look stuck. It is not. Registering the schema happens on Microsoft's servers and typically takes 5 to 15 minutes. You will see:

[INF] Connection state Draft.
[INF] Connection state Draft.
[INF] Connection state Ready.

Only after "Ready" does anything get written. If you want to watch it separately, open another window and run deploy\Watch-SchemaRegistration.ps1.

Before this run, understand that the schema is permanent. Once registered, no property's type or behaviour can ever be changed. Correcting a mistake means deleting the connection and every item in it. If you are unsure about the schema, stop and review the dry run output first.

What success looks like:

[INF] Crawl run 2 closed as succeeded.
[INF] Ingestion complete. 3 row(s) processed ... failed=0 ...

followed by a timing table. Check $LASTEXITCODE is 0.

4.3 Confirm the data really arrived

Do not trust the log alone. Ask the two systems independently.

Ask the state database what it recorded:

sqlcmd -S <server> -E -C -I -d ConnectorState -Q "SET NOCOUNT ON;
SELECT RunId, Status, ItemsRead, ItemsWritten, ItemsFailed FROM crawl.vwRunHistory;"

Ask Microsoft what it holds. The simplest check is in the Microsoft 365 admin centre, under Search & intelligence → Data sources: your connection should be listed and show an item count. It can lag by a few minutes.

Part 5. The tests, in order

Each test states what it proves, why that matters, exactly what to do, and what failure looks like. Run them in this order — several depend on the state left by the one before.

Test 1 — Change detection

Proves: the connector recognises unchanged items and skips them.
Why it matters: without this, every crawl rewrites the whole corpus, which is slow, wasteful, and burns your Microsoft write quota.

Do: run the tool a second time, immediately, changing nothing.

Expect: unchanged equals nearly everything, processed near zero, batches=0, and a far shorter run.

If it fails — if the second run writes everything again — your item IDs are not stable between runs. Something in the source query is generating a different ID for the same row. This is the most important early failure to catch.

Test 2 — Delete detection

Proves: removing something at the source removes it from Copilot.
Why it matters: a document deleted for a reason must stop being answerable. This is a compliance property, not a tidiness one.

Do: mark one row deleted at the source (however your source expresses that), then run a full crawl. Pick a second row and leave it alone, as a control.

Expect: deleted=1, and a log line saying the sweep will remove one item.

Verify on three surfaces, because any one alone can mislead:

-- the state database should mark it deleted (State 3)
sqlcmd -S <server> -E -C -I -d ConnectorState -Q "SET NOCOUNT ON;
SELECT ItemId, State FROM crawl.Item WHERE ItemId IN ('<deleted-id>','<control-id>');"

and confirm the deleted one is gone from the index while the control is still there.

Test 3 — Undelete

Proves: the previous test is reversible, and the corpus was not rebuilt around the gap.

Do: restore the row at the source, run a full crawl.

Expect: the item returns, its state goes back to 1 (live), and deleted=0.

Test 4 — The delete guard

Proves: a source that suddenly returns far fewer rows does not empty your index.
Why it matters: the likeliest cause of a big deletion is not a big deletion. It is a dropped view, a revoked permission, or a filter that matched nothing. The guard exists to refuse that.

Before you start, do this arithmetic. The guard compares a percentage, stored to two decimal places. On a corpus of 100,000 items, one missing item is 0.001 per cent, which stores as 0.00 — so even a guard set to zero will not catch it. Work out how many items your threshold really represents:

-- how many missing items does a zero guard actually catch?
sqlcmd -S <server> -E -C -I -d ConnectorState -Q "SET NOCOUNT ON;
DECLARE @live INT = (SELECT COUNT(*) FROM crawl.Item WHERE ConnectionId='<id>' AND State=1);
SELECT n AS missing, CAST(100.0*n/@live AS DECIMAL(5,2)) AS stored_pct
FROM (VALUES (1),(2),(5),(6),(10),(20)) v(n);"

The first row whose stored_pct is above 0.00 is the smallest loss the guard can see.

Do: set "MaxDeletePercent": "0" in Settings, remove at least that many rows at the source, run a full crawl.

Expect: the run fails with exit 4 and a message naming both numbers:

Delete sweep refused. It would remove 6 of 111799 live items (0.01%), above the 0.00% guard.

Then recover: restore the rows, remove the MaxDeletePercent override, run again, and confirm health returns to normal. A failed run stays in the history — that is intended.

Test 5 — The run lock

Proves: two crawls cannot run at once.
Why it matters: two simultaneous crawls can delete each other's data.

Do: start the tool, wait two seconds, start it again in another window.

Expect: the first exits 0. The second exits 5 and prints a message naming the run that holds the lease, its host, its process ID and its last heartbeat.

Remember exit 5 is not a failure. If your monitoring treats it as one, it will alert every time this works correctly.

Test 6 — Incremental crawling

Proves: the connector can read only what changed.

Do: point Source:ItemView at your incremental view, set "Incremental": "true", and run twice.

Expect: the first may be escalated to a full crawl, with the reason stated — there is no checkpoint yet to be a difference from. The second opens in Incremental mode and reports where it resumed from.

A guard you may hit: if the view has no "last modified" column the tool exits 2 and names the view you should be using instead. That is correct behaviour, not a fault.

Test 7 — Throttling

Proves: the connector survives Microsoft asking it to slow down.
Why it matters: at any real volume this will happen. The question is whether items are lost.

Do: nothing special. Read the counters from your largest run.

Expect: throttleWaits above zero with failed=0. Thousands of waits with nothing lost is a pass. Any non-zero failed is not.

Test 8 — The scheduled cleanup job

Proves: run history is trimmed automatically, so the state database does not grow without limit.

Do:

sqlcmd -S <server> -E -C -I -d ConnectorState -i sql\27-crawl-state-retention-job.sql -b
sqlcmd -S <server> -E -C -I -d msdb -Q "EXEC dbo.sp_start_job @job_name = N'ConnectorState - purge crawl history';"

Wait half a minute, then read the outcome:

sqlcmd -S <server> -E -C -I -d msdb -Q "SET NOCOUNT ON;
SELECT TOP 3 step_name, run_status, LEFT(message,120) FROM msdb.dbo.sysjobhistory h
JOIN msdb.dbo.sysjobs j ON j.job_id=h.job_id
WHERE j.name = N'ConnectorState - purge crawl history' ORDER BY instance_id DESC;"

Expect: run_status = 1 and a message naming each connection purged. This test is impossible on LocalDB, which has no SQL Server Agent.

Test 9 — Least privilege

Proves: the connector's own database account can do what it needs and nothing more.

Do:

sqlcmd -S <server> -E -C -I -d ConnectorState -i sql\42-verify-least-privilege.sql -b

Expect: every writer procedure reachable, every reader view reachable, and every attempt to touch the tables directly refused. This script needs no accounts of its own — it creates temporary users internally — so it works even where the named service accounts do not exist.

Test 10 — Nothing sensitive reaches the logs

Proves: log files can be shared with support without leaking customer data.

Do: take some real text from your source — a customer name, a description — and search every log for it:

Select-String -Path C:\Connectors\*\Logs\*.log -SimpleMatch "<a real value from your data>"

Expect: no matches. The logs should contain item IDs, counts and byte sizes only.

Part 6. The dashboard

6.1 What it is

A small internal website showing crawl history, run detail and connection health. It is read-only — it cannot start a crawl or change anything — and it is how you learn a crawl failed without reading log files.

6.2 Install it

dotnet publish src\ConnectorState.Dashboard -c Release -o artifacts\dashboard

Then, from an elevated Windows PowerShell 5.1 prompt — not PowerShell 7, see trap T4:

.\deploy\Install-Dashboard-IIS.ps1 -SiteName ConnectorState `
    -PhysicalPath C:\inetpub\ConnectorState `
    -SourcePath .\artifacts\dashboard -HttpPort 8080 -HttpsPort 8443

6.3 Give it permission to read

The website runs as its own Windows identity, named after the site: IIS APPPOOL\ConnectorState. That identity has no access to your database yet, so every page will return HTTP 500 until you grant it:

sqlcmd -S <server> -E -C -I -d master -Q "IF SUSER_ID('IIS APPPOOL\ConnectorState') IS NULL
    CREATE LOGIN [IIS APPPOOL\ConnectorState] FROM WINDOWS;"
sqlcmd -S <server> -E -C -I -d ConnectorState -Q "
    IF DATABASE_PRINCIPAL_ID('IIS APPPOOL\ConnectorState') IS NULL
        CREATE USER [IIS APPPOOL\ConnectorState] FOR LOGIN [IIS APPPOOL\ConnectorState];
    ALTER ROLE [crawl_reader] ADD MEMBER [IIS APPPOOL\ConnectorState];"

A 500 here is almost never a code fault. It is this grant.

6.4 Restricting who can see it

Set CrawlState:ReaderGroups in the site's appsettings.json to a Windows or Entra group. Members see the pages; everyone else gets HTTP 403.

The application does not notice the change until it restarts. Touch web.config to recycle it:

(Get-Item C:\inetpub\ConnectorState\web.config).LastWriteTime = Get-Date

Skip that and your change appears to do nothing, which is easy to misread as the feature not working.

You can test both directions with one account: point it first at a group you are not in (expect 403), then at one you are (expect 200).

Part 7. Running it regularly

7.1 Scheduling

Nothing invokes the connector on its own. You schedule it, typically with Windows Task Scheduler, and the repository provides deploy\Schedule-Connectors.ps1 to set that up.

One task, one process, running the connectors in sequence — not several tasks with staggered start times. Task Scheduler has no way to say "start this when that one finishes", so staggered tasks eventually overlap when one runs long, and then the run lock refuses one of them every night.

Your monitoring must treat exit 5 as success. It means "another crawl was already running", which is the design working. A rule that pages on any non-zero exit will page somebody at 3am for correct behaviour, and the rule will be switched off, and then a real failure will be missed too.

7.2 A sensible pattern

WhenWhatWhy
Every few hoursIncremental crawlKeeps content fresh cheaply. Cannot detect deletions.
Nightly or weeklyFull crawlThe only thing that detects deletions and refreshes permissions.
WeeklyReconciliationdeploy\Compare-SourceToIndex.ps1 compares the source against the index and reports drift.

The gap between full crawls is your permission staleness window. If someone loses access at the source today and the next full crawl is in seven days, Copilot may keep showing them that content for seven days. Choose that interval deliberately, and write down who accepted it.

Part 8. Releasing a new version

Only relevant if you are changing the code. Four steps, and only the third is done by hand.

  1. Tag both lines together. This repository ships two builds from the same source: a current one and one for older tooling. Tag vX.Y.Z on the main branch and vX.Y.Z-net9 on the other. They must carry the same version.
  2. Automation builds each tag and creates a draft release with the deployment package, the offline package set, and checksums attached.
  3. A person publishes the two drafts. The automation never publishes, deliberately — the package is something somebody signs off.
  4. Retire what the new release supersedes, by running the retirement workflow manually.

Retirement deletes releases and keeps every tag. A release is a download page; the tag is the exact code it was built from. Deleting the tag would break every attempt to check out that version later, for the sake of tidying a downloads page.

Two things that surprise people:

  • A tag is not a release. If any part of the build fails, the release step is skipped and you have a tag with nothing attached. Always check the release page, not just that the tag exists.
  • A draft is not downloadable. So a draft cannot be your rollback target. Keep at least two published versions if you want somewhere to roll back to.

Before pushing anything, check you are not committing secrets. Search the change for identifiers, internal hostnames and credential names, and run a secret scanner over the whole history, not just your change — something committed weeks ago is still exposed.

Part 9. The traps

Each of these has cost real time. They are ordered by when you are likely to meet them.

#TrapWhat happens, and what to do
T1Using LocalDBIt looks like SQL Server and mostly behaves like it, but it has no SQL Server Agent, so the scheduled cleanup cannot run and Test 8 is impossible. Use a full instance, even a free Developer edition one.
T2Running script 24 before script 40The most common deployment failure. Script 24 creates a procedure that reads a column script 40 adds. SQL Server tolerates a missing table but not a missing column, so script 24 fails with Msg 207, and then the grant on the procedure it did not create fails with Msg 15151. So a schema mistake reports itself as a permissions problem and sends you looking in the wrong place. It is invisible when upgrading an existing database and appears only when building a new one.
T3-d does not redirect the scriptsEvery script contains USE [ConnectorState]. The -d flag sets only the starting database. A script run "against test" therefore builds in production and reports success. Use deploy\Invoke-StateScripts.ps1 for any other database name. This is the most dangerous item here because the failure is silent and in the wrong direction.
T4Running the IIS installer under PowerShell 7It uses Windows-feature commands that do not exist in PowerShell 7, and dies at the first step with Class not registered — which reads like a broken IIS rather than a wrong shell. Use Windows PowerShell 5.1, elevated.
T5Omitting -I from sqlcmdSome tables use a SQL feature that requires a setting sqlcmd leaves off by default. You get Msg 1934 and a message about indexed views that has nothing to do with your problem. Always pass -I.
T6HTTP 500 from the dashboardAlmost always the website's identity lacking database access, not a code fault. Each site has its own identity, IIS APPPOOL\<SiteName>, and a second site needs its own grant. See 6.3.
T7Changing dashboard settings and seeing no effectThe application reads its configuration once at startup. Touch web.config to recycle it. Without this, a test of the permission settings returns the same answer every time and proves nothing.
T8Expecting a zero delete guard to block one itemThe guard compares a percentage stored to two decimal places. On 100,000 items a single missing row rounds to 0.00 and passes. Compute how many items your threshold really represents before testing it, and agree the threshold in items as well as percent.
T9Treating exit 5 as a failureIt means another crawl was already running. That is the lock doing its job. Alerting on it pages people for correct behaviour.
T10Assuming the schema can be correctedIt cannot. A registered schema is append-only: you may add a property, but no property's type or behaviour can ever change. Fixing a mistake means deleting the connection and every item in it. Review the dry run output before the first real push.
T11Storing the secret as the wrong userCredential Manager is per-user. Store it as yourself and run the connector as a service account, and it will not be found — exit 3, with a message about the credential. Store it under the account that will run it.

Part 11. A checklist you can tick off

Before you start

  • App registration exists, with both permissions and admin consent granted
  • Entra group object ID collected
  • Read-only SQL login on the source
  • Permission to create a database
  • Full SQL Server with Agent running (not LocalDB)
  • Secret stored in Credential Manager, under the account that will run the connector
  • Every value in table 1.3 filled in

Deployment

  • Build succeeds with zero warnings, tests pass
  • Tools published outside the repository
  • File paths in script 20 edited to real ones
  • All scripts run in order, 40 before 24, each one's output read
  • Object counts match: 8 tables, 7 views, 30 procedures, 6 table types
  • Settings file completed in the published folder
  • Dry run clean
  • First real run exits 0, and the data is visible independently of the log

Tests

  • Change detection: second run reports nearly everything unchanged
  • Delete detection: verified on three surfaces, with a control
  • Undelete: the item comes back
  • Delete guard: refuses, with the arithmetic done first
  • Recovery: health returns to normal
  • Run lock: second concurrent run exits 5
  • Incremental: resumes rather than re-reading
  • Throttling: waits above zero, failures at zero
  • Cleanup job: runs and names what it purged
  • Least privilege: writer refused direct table access
  • Logs: no source content anywhere in them

Before going live

  • Schedule created, and exit 5 treated as success by monitoring
  • Full-crawl interval chosen deliberately, and the permission staleness window written down and accepted by a named person
  • Delete threshold agreed in items as well as percent
  • Somebody named as the person woken when a crawl fails
  • Secret expiry date recorded, with a reminder before it

The last four are not engineering tasks, and clearing every technical item above does not answer a single one of them. They are the difference between something that works and something that is supported.
