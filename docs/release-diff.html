Feature 2

Deletion, without asking the source

The sweep diffs the inventory against what a full run saw. A hard DELETE, a row leaving the query and a permission change that hides it are one question. No soft-delete column is needed, and one being present buys nothing.

Features 3 and 10

Only what moved is written

Content and ACL hash separately, and both are compared. On a steady-state run most items are already correct, and the write that is skipped is the expensive one.

Throughput

Twenty at a time

Writes go through $batch with per-item outcomes, so one refused item no longer abandons the other nineteen. Settings:Batch = false restores the previous path.

What v1.3.1 changed, and why there was a v1.3.1

v1.3.0 shipped, and a verification pass over its own diff then found five defects in it. Two would have been felt: ItemHasher shifted an Unspecified DateTime by the host’s local offset — and Unspecified is exactly what SqlDataReader.GetDateTime returns — so two connectors in different timezones would each have rewritten every one of the other’s items, on every run; and sql/20 guarded only CREATE DATABASE, so re-running it reverted a FULL recovery model and killed live sessions on a database already serving a crawl.

The other three: an INT overflow in the paging arithmetic, tombstone retention aged on the wrong column, and three table scans where one aggregate does. All five are in v1.3.1 and this page describes the fixed code.

The guard to understand before deploying

uspGetPendingDeletes refuses any sweep that would remove more than ten percent of the live corpus, and refuses one after an incremental run outright. A threshold rather than a flag, because the realistic failure is not a missing row but a missing set: a view redefined, a WHERE clause that stopped matching, a permission revoked, a source restored to last month. Each produces a run that completes cleanly and reads too little, and each would otherwise have the difference swept out of the index.

Clearing it takes Settings:OverrideDeleteGuard and a deliberate decision. A retry will not do it.

The line that looks like bookkeeping and is not

An item found unchanged is not written — that is the whole optimisation — but it must still be marked seen. Skipping the write and skipping the mark are one line apart in FlushChunkAsync and produce opposite outcomes: the first is the saving, the second has the next full crawl conclude the source dropped every item that did not change, and remove them. The corpus empties one run at a time, starting with whatever is most stable.

What has and has not been verified

None of this has run against a real SQL Server or a real tenant. All seven scripts are unexecuted, the dashboard has never rendered a row, and Settings:Batch defaults on — so the first production run uses a write path that has never spoken to Graph. 311 tests pass and every project builds; that is a different claim. Each SQL file carries a verification block at its foot for a scratch instance.

sql/26 is the one to treat differently. The other six create a separate database and are reversible by dropping it. sql/26 adds columns and installs cascading triggers on the customer’s source tables. It is independent: defer it and everything else still works, at differencing rather than incremental reads.
